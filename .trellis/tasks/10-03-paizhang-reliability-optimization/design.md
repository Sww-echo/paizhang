# 牌账同步可靠性与工程优化设计草案

## 定位

这是优化待办的建议方案，不代表已经获准开始实现。实施前复核最新代码、服务端迁移状态及产品排期；尤其不能把旧任务延期的离线体验或发布工作自动恢复为当前必做项。

## 原则

1. 先数据正确性，再减少请求，最后拆分展示代码。
2. 先补可复现的回归测试，避免重构时丢失现有行为。
3. 页面逐步以本地可观察状态为数据来源；远端同步由统一协调层负责。
4. 服务端权限和事务校验是最终边界，本地状态不能替代授权。
5. 保留既有技术栈与已生效保护，不强制引入新状态管理框架。

## 建议设计

### 账号与本地迁移（R1、R2）

- 操作记录绑定 actorId；队列、可见缓存和控制器生命周期都按当前会话隔离。
- 会话变化使旧同步任务失效；每次执行操作前检查账号，异步返回后检查代际。
- 升级 Drift schema 时为旧数据制定迁移测试。历史队列若无法可靠识别归属，应保留并隔离为待处理数据，不能直接归给当前账号或静默删除。
- 远端已确认数据与待同步变化分开保存，展示层合并。业务变化与操作入队应在同一事务内保持一致。
- 确认成功后更新基线并移除对应待同步变化；拒绝/冲突保留输入和可见原因。
- 缓存补齐版本及必要资料；退出、成员移除和房间访问失效分别定义缓存可见范围，遵守现有历史访问边界。

### 队列恢复与版本冲突（R3、R4）

- 区分可重试网络错误、权限/状态业务拒绝、版本冲突。
- 网络重试使用带上限的退避；启动、回前台和网络恢复共用合并后的触发入口。
- 按房间/实体保持依赖顺序，隔离失败依赖链，不让一条永久失败冻结全局队列。
- RPC 更新/撤销/恢复增加基础版本比较；仍保留 operationId 幂等。
- 连续离线编辑同一回合必须设计版本衔接或操作合并，不能机械地让每条都提交相同旧版本。
- RPC 签名、权限和客户端升级通过新的迁移协调，不直接重写已部署迁移。

### 房间状态与刷新（R2、R6、R7）

- 提取房间控制器，统一快照、加载状态、待同步数量、失败操作和权限派生状态。
- 首屏、用户刷新、操作成功、Realtime 事件均走统一刷新协调入口。
- 保留现有事件合并和生命周期代际保护，补充同一生命周期内的请求顺序保护。
- 监听订阅状态，订阅建立和重连时重新对账；刷新中保留可用旧内容。
- 优先移除重复首刷、批量更新、缓存资料；再根据测量决定增量协议。
- 历史先摘要后明细，分页需要稳定的复合排序或游标；保持离开成员的历史权限边界。

### 可测试性与错误边界（R5、R7、R8）

- 提供最小仓储接口及可注入的时钟、网络/订阅事件来源，便于确定性测试。
- 生产控制器由真实或 Fake Repository 驱动；内存服务不再被当作正式 RPC 的验证替代品。
- 错误在基础设施/应用边界转换为统一类型；页面只负责提示和下一步操作。
- 邀请分别维护待处理、处理中、已成功状态；失败不进入永久去重集合。
- 日志记录操作标识、错误码和恢复结果，避免记录个人联系方式、认证 token 和邀请凭据。

## 建议实施顺序

1. Phase 0：任务落盘，保留当前验证基线；确认排期后再启动。
2. Phase 1：R1、R3、R4 及对应回归测试；引入最小注入点。
3. Phase 2：R2，本地恢复与待同步合并；验证旧数据库迁移和重启场景。
4. Phase 3：R6，统一刷新、重连对账及批量/按需加载；记录性能对比。
5. Phase 4：R7、R8，基于已稳定的业务协调层拆页面并统一错误体验。
6. Phase 5：R9，CI、开发说明与发布前核验；真实 Supabase/多设备验收单独记录。

R5 的测试应贯穿每个阶段，不延后到所有改动结束才补。

## 验证策略

- 本地：`flutter analyze --no-pub`、`flutter test --no-pub`、`git diff --check`。
- 有 Dart 修改时增加格式检查；有平台或资源修改时执行对应构建。
- 数据库：临时测试环境执行迁移、RPC/RLS 与双客户端冲突测试，不使用生产数据。
- 离线：覆盖进程重启、同设备账号切换、前台网络恢复、远端拒绝和并发快照刷新。
- 性能：记录首屏请求数、历史数据规模、快照耗时和本地写入量；没有实测时不宣称性能提升比例。
- 发布：CI 构建不能替代真实设备的 release 网络、深链和签名验收。
